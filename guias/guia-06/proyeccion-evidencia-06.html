Enfoque Práctico ADSO

El Reto: Conectar la BD con el Software de su Negocio

Proyecto Formativo

Esta evidencia no es un ejercicio genérico: debe construirse pensando en el software que cada equipo de aprendices está creando para solucionar una necesidad de negocio real (tienda e-commerce, gestión hospitalaria, trazabilidad agropecuaria, reservas hoteleras, facturación).

1

Entidades Centrales

Identifiquen los actores y objetos vitales del negocio: Usuarios, Roles, Clientes, Productos, Transacciones, Facturas o Reservas.

2

Tipos de Datos Exactos

Cada campo debe tener el tipo de dato físico óptimo: DECIMAL para montos monetarios, DATETIME para marcas de tiempo, y longitudes de VARCHAR acordes a la realidad.

3

Blindaje con Restricciones

La base de datos debe impedir datos corruptos: correos repetidos (UNIQUE), precios negativos (CHECK) o ventas huérfanas sin cliente (FK NOT NULL).

Recomendación del Instructor: Para esta evidencia se recomienda modelar un módulo representativo de su proyecto que contenga entre 5 y 8 tablas fuertemente relacionadas, evidenciando relaciones 1:N y tablas intermedias N:M con políticas de borrado.
Caso Práctico Paso a Paso

Empresa Modelo: "AgroTech Colombia S.A.S."

Sistema Comercial y Ventas

Tomaremos como referencia para esta sesión el sistema de gestión comercial de "AgroTech Colombia S.A.S.", empresa dedicada a la distribución mayorista de insumos agrícolas en el Huila con portal web transaccional. Modelaremos 6 tablas clave:

1. roles

Perfiles de seguridad: ADMIN, VENDEDOR, CLIENTE. Llave primaria id_rol.

2. usuarios

Cuentas con email UNIQUE, contraseña encriptada, id_rol FK y estado activo/inactivo.

3. categorias

Líneas de insumos (Semillas, Fertilizantes, Riego). Código único y nombre no nulo.

4. productos

Catálogo con SKU único, precio_unitario > 0, stock >= 0 y id_categoria FK.

5. pedidos

Cabecera de compras con número de factura único, fecha automática, cliente id_usuario FK y total.

6. detalle_pedidos

Tabla asociativa N:M (pedidos-productos). cantidad > 0, precio capturado y cascada al borrar pedido.

Esquema Relacional: agrotech_db (MySQL 8.0 InnoDB Engine) 1:N (roles→usuarios), 1:N (cat→prod), N:M (pedidos⇄productos)
Herramienta de Modelado

¿En qué Programa lo Hacen? MySQL Workbench

MySQL Workbench 8.0 CE

La guía exige explícitamente: "Se debe realizar la creación de los diseños de bases de datos en MySQL WorkBench". En Workbench trabajaremos con dos módulos fundamentales:

1. Modelador Gráfico EER (Data Modeling)

Genera el archivo nativo .mwb

Lienzo visual donde se dibujan las tablas, atributos, tipos de datos, llaves primarias y las líneas de relación foráneas.

Ruta: Menú File > New Model > Doble clic en "Add Diagram".

2. Forward Engineering y Editor SQL

Genera el script ejecutable .sql

¡Atención Aprendiz!: La evidencia requiere entregar tanto el archivo nativo .mwb (para abrirlo y calificar su diseño visual) como el documento Word explicativo y el script .sql.
Paso a Paso en MySQL Workbench

Paso 1: Dibujar Tablas y Asignar Tipos de Datos

Herramienta: Table (T)

En el panel lateral izquierdo del EER Diagram, selecciona el icono "Place a new Table" (o presiona la tecla T) y haz clic sobre el lienzo. Al hacer doble clic sobre la tabla creada, se abrirá el editor inferior:

Tabla: usuarios Motor: InnoDB
id_usuario : INT (PK, NN, AI)
id_rol : INT (NN, FK a roles)
nombre_completo : VARCHAR(100) (NN)
email : VARCHAR(120) (NN, UQ)
password_hash : VARCHAR(255) (NN)
telefono : VARCHAR(15)
estado : VARCHAR(15) (DEFAULT 'ACTIVO')
fecha_registro : DATETIME (DEFAULT CURRENT_TIMESTAMP)
Tabla: productos Motor: InnoDB
id_producto : INT (PK, NN, AI)
id_categoria : INT (NN, FK a categorias)
sku : VARCHAR(30) (NN, UQ)
nombre_producto : VARCHAR(120) (NN)
precio_unitario : DECIMAL(12,2) (NN, CHECK > 0)
stock_disponible : INT (NN, CHECK >= 0)
activo : TINYINT(1) (DEFAULT 1)
Criterio Técnico: Prohíbe el uso de VARCHAR para todo. Los valores de moneda siempre deben ser DECIMAL(12,2) para evitar errores de redondeo financiero de punto flotante.
Restricciones de Columna

Paso 2: Banderas de Columna (Column Flags) en Workbench

PK • NN • UQ • AI

En la pestaña Columns de MySQL Workbench se activan las casillas de verificación que definen el comportamiento y las restricciones de cada campo:

PK Primary Key

Identificador unívoco obligatorio. Impide duplicados y nulos.

NN Not Null

Obligatorio. No permite que la columna quede vacía.

UQ Unique Index

Garantiza unicidad absoluta (ej. email, SKU, número de factura).

AI Auto Increment

Genera un ID numérico correlativo (1, 2, 3...) automáticamente.

// Ejemplo en SQL resultante del modelado:
CREATE TABLE usuarios (
  id_usuario INT AUTO_INCREMENT,
  email VARCHAR(120) NOT NULL,
  estado VARCHAR(15) DEFAULT 'ACTIVO',
  PRIMARY KEY (id_usuario),
  UNIQUE INDEX uq_usuario_email (email ASC)
) ENGINE = InnoDB;
Integridad Referencial

Paso 3: Trazar Relaciones y Llaves Foráneas (FK)

Herramienta 1:n Non-Identifying

Para relacionar dos tablas en el EER Diagram de MySQL Workbench:

1 Elegir Herramienta

Selecciona en la barra lateral el icono 1:n Non-Identifying Relationship (línea discontinua).

2 Orden de Clics

Haz clic primero en la tabla hija (ej. pedidos) y luego en la tabla padre (ej. usuarios).

3 Pestaña Foreign Keys

En el editor inferior, renombra la restricción con prefijo claro: fk_pedidos_usuarios y enlaza la columna exacta.

// Cláusula FOREIGN KEY generada por Workbench:
CONSTRAINT fk_pedidos_usuarios
  FOREIGN KEY (id_usuario)
  REFERENCES usuarios (id_usuario)
  ON DELETE RESTRICT
  ON UPDATE CASCADE;
Reglas de Negocio Referenciales

Paso 4: Configurar Políticas ON DELETE y ON UPDATE

RESTRICT vs CASCADE vs SET NULL

En la pestaña Foreign Keys, a la derecha, MySQL Workbench permite configurar qué ocurre en la tabla hija cuando un registro padre se elimina o actualiza:

RESTRICT / NO ACTION

Bloquea la eliminación. Si intentas borrar un Cliente que ya tiene pedidos facturados, MySQL genera un error y cancela la operación para proteger el historial contable.

Uso: Clientes, Roles, Categorías
CASCADE

Elimina en cadena. Si se anula o elimina un pedido, automáticamente el motor borra todas sus líneas asociadas en detalle_pedidos sin dejar basura.

Uso: Detalles de comprobantes
SET NULL

Pone el valor en NULL. Si se elimina el vendedor asignado a un cliente, el cliente no se borra; el campo id_vendedor pasa a ser NULL.

Uso: Asignaciones opcionales
Requisito para el documento Word: La guía pide justificar por qué se eligió cada restricción. Debes argumentar la lógica de negocio detrás de cada CASCADE o RESTRICT.
Validación de Dominio (MySQL 8+)

Paso 5: Restricciones CHECK (Dominio e Integridad)

CONSTRAINT ... CHECK (...)

A partir de MySQL 8.0, las cláusulas CHECK son evaluadas y forzadas activamente. Si una sentencia INSERT o UPDATE viola la condición, el motor rechaza la transacción con el Error Code: 3819:

// 1. Precio de venta estrictamente positivo:
ALTER TABLE productos
ADD CONSTRAINT chk_precio_positivo
CHECK (precio_unitario > 0);

// 2. Stock no puede ser negativo:
ALTER TABLE productos
ADD CONSTRAINT chk_stock_no_negativo
CHECK (stock_disponible >= 0);
// 3. Cantidad comprada mayor a cero:
ALTER TABLE detalle_pedidos
ADD CONSTRAINT chk_cantidad_minima
CHECK (cantidad > 0);

// 4. Total del pedido nunca negativo:
ALTER TABLE pedidos
ADD CONSTRAINT chk_total_positivo
CHECK (total_neto >= 0);
Cómo agregarlo en Workbench: En el editor de tabla, pestaña Inserts o pestaña DDL, puedes redactar directamente las restricciones CHECK para que queden guardadas dentro del modelo .mwb.
Generación de Código Físico

Paso 6: Forward Engineering en MySQL Workbench

Ctrl + G • Database Menu

Una vez finalizado el modelo gráfico en el lienzo, realizamos el proceso de Ingeniería Hacia Adelante (Forward Engineering) para compilar el diagrama visual en el script SQL físico y crear el esquema en el servidor:

Paso A

Ve a Database > Forward Engineer... o presiona Ctrl + G.

Paso B

Marca: "Generate DROP Statements Before Each CREATE" para permitir re-ejecución limpia.

Paso C

Exporta y guarda el script generado como script_estructura_bd.sql.

Paso D

Ejecuta sobre tu servidor local hasta ver la pantalla de "Forward Engineer Finished Successfully".

-- Script DDL Autogenerado por MySQL Workbench:
CREATE SCHEMA IF NOT EXISTS `agrotech_db` DEFAULT CHARACTER SET utf8mb4;
USE `agrotech_db`;

CREATE TABLE IF NOT EXISTS `roles` (
  `id_rol` INT NOT NULL AUTO_INCREMENT,
  `nombre_rol` VARCHAR(45) NOT NULL,
  PRIMARY KEY (`id_rol`),
  UNIQUE INDEX `uq_rol_nombre` (`nombre_rol` ASC)
) ENGINE = InnoDB;
Evidencia de Desempeño

Paso 7: Probar que las Restricciones Funcionan

Testeo de Errores MySQL

Para obtener el puntaje máximo en la evidencia, debes demostrar en el informe de Word que la base de datos rechaza activamente los datos inválidos mediante capturas de Workbench:

1. Violación de Llave Foránea (FK) Error 1452
INSERT INTO usuarios (id_rol, nombre_completo, email)
VALUES (999, 'Pedro Gómez', 'pedro@correo.com');

Respuesta de MySQL: "Cannot add or update a child row: a foreign key constraint fails". (Protección: id_rol 999 no existe en tabla roles).

2. Violación de Restricción CHECK Error 3819
INSERT INTO productos (nombre_producto, precio_unitario)
VALUES ('Abono Orgánico', -15000);

Respuesta de MySQL: "Check constraint 'chk_precio_positivo' is violated". (Protección: el precio debe ser > 0).

Tip para el documento: Incluye una tabla comparativa: "Restricción probada", "Sentencia errónea enviada", "Código de Error de MySQL Workbench" y la captura de pantalla con el icono rojo en el Action Output.
