Buenas Prácticas de Ingeniería de Software

Anatomía de un Script Maestro (Idempotente y Autónomo)

100% Reproducible

Un script de base de datos para producción debe ser idempotente: poder ejecutarse 1, 10 o 100 veces en cualquier máquina sin fallar, dejando siempre la base de datos en un estado limpio, consistente y listo para funcionar:

1 Cabecera y Sesión

Metadatos (autor, fecha, versión), codificación utf8mb4 y desactivación temporal de FOREIGN_KEY_CHECKS.

2 Borrado y Creación DDL

DROP DATABASE IF EXISTS, creación del esquema y sentencias CREATE TABLE ordenadas por jerarquía referencial.

3 Datos Semilla (Seeders)

Poblado inicial DML: roles base, usuarios administradores, catálogos y transacciones de prueba coherentes.

4 Consultas DQL (Test)

Consultas multitable con INNER JOIN al final del script para certificar que las relaciones devuelven datos reales.

Criterio de Evaluación: El instructor abrirá el script en una instancia limpia de MySQL Workbench y presionará el rayo de ejecución. Si el script falla por orden incorrecto de tablas o llaves inexistentes, la evidencia no podrá ser aprobada.
Caso de Referencia Empresarial

Software Modelo: "AgroTech Colombia S.A.S."

Esquema: agrotech_db

Consolidamos el script maestro para la plataforma web y móvil de gestión comercial e inventario de AgroTech Colombia S.A.S., integrando el diseño EER de la EV02 en un archivo SQL físico completo:

1. roles (Maestra)

Catálogo de accesos: ADMIN, VENDEDOR, CLIENTE. Sin dependencias externas.

2. categorias (Maestra)

Líneas de producto: Semillas, Fertilizantes, Herramientas, Riego. Sin dependencias externas.

3. usuarios (Dependiente)

Clientes y personal. Depende de roles(id_rol). Restricción email UNIQUE.

4. productos (Dependiente)

Catálogo comercial. Depende de categorias(id_categoria). CHECK precio > 0.

5. pedidos (Transaccional)

Facturación. Depende de usuarios(id_usuario). numero_factura UNIQUE.

6. detalle_pedidos (Asociativa)

Líneas de venta N:M. Depende de pedidos y productos. CHECK cantidad > 0.

Regla de Orden DDL: Crear primero tablas independientes $ ightarrow$ luego tablas dependientes. Inverso para DROP

Estructura del Script SQL • Paso 1

Encabezado, Parámetros de Sesión y Creación de BD

Control de Entorno

Todo script profesional comienza con una cabecera de metadatos institucionales y directivas de control de sesión para garantizar compatibilidad multiplataforma y caracteres especiales (acentos y letra ñ):

-- =======================================================================
-- PROYECTO FORMATIVO: AgroTech Colombia S.A.S. (Plataforma Comercial e Inventario)
-- EVIDENCIA: GA6-220501096-AA2-EV03: Script bases de datos del proyecto
-- PROGRAMA: Tecnología en Análisis y Desarrollo de Software (ADSO Virtual - Ficha 228118)
-- CENTRO: CADPH Garzón • Regional Huila • SENA
-- MOTOR: MySQL Community Server 8.0+ | Engine: InnoDB | Charset: utf8mb4
-- =======================================================================

-- 1. Parámetros de Sesión Segura e Idempotencia:
SET NAMES 'utf8mb4';
SET time_zone = '-05:00'; -- Zona horaria Colombia
SET FOREIGN_KEY_CHECKS = 0; -- Evita bloqueos en borrado inicial

-- 2. Borrado Limpio y Creación de la Base de Datos:
DROP DATABASE IF EXISTS `agrotech_db`;
CREATE DATABASE `agrotech_db`
  DEFAULT CHARACTER SET utf8mb4
  DEFAULT COLLATE utf8mb4_unicode_ci;

USE `agrotech_db`;
Explicación: FOREIGN_KEY_CHECKS = 0 permite eliminar y recrear el esquema sin disparar bloqueos por tablas secundarias. Al final del script se vuelve a activar con 1.
Estructura del Script SQL • Paso 2

Bloque DDL: Creación de Tablas Maestras e Independientes

roles y categorias

Las primeras tablas que se deben crear son aquellas que no tienen llaves foráneas hacia otras tablas (entidades fuertes o de catálogo base):

-- 1. Tabla de Roles de Seguridad:
CREATE TABLE `roles` (
  `id_rol` INT NOT NULL AUTO_INCREMENT,
  `nombre_rol` VARCHAR(45) NOT NULL,
  `descripcion` VARCHAR(150) NULL,
  PRIMARY KEY (`id_rol`),
  UNIQUE INDEX `uq_rol_nombre` (`nombre_rol` ASC)
) ENGINE = InnoDB;
-- Almacena perfiles de acceso autorizados
-- 2. Tabla de Categorías de Insumos:
CREATE TABLE `categorias` (
  `id_categoria` INT NOT NULL AUTO_INCREMENT,
  `codigo_categoria` VARCHAR(20) NOT NULL,
  `nombre_categoria` VARCHAR(80) NOT NULL,
  `activo` TINYINT(1) NOT NULL DEFAULT 1,
  PRIMARY KEY (`id_categoria`),
  UNIQUE INDEX `uq_cat_codigo` (`codigo_categoria` ASC)
) ENGINE = InnoDB;
-- Clasificación del catálogo agroempresarial
Detalle Técnico: Siempre especifica explícitamente ENGINE = InnoDB. InnoDB es el motor estándar de MySQL que garantiza transacciones ACID y verificación real de llaves foráneas.
Estructura del Script SQL • Paso 3

Bloque DDL: Tablas con Integridad Referencial (FK y CHECK)

usuarios y productos

Una vez creadas las maestras, se definen las tablas que apuntan hacia ellas con cláusulas CONSTRAINT FOREIGN KEY y políticas de restricción:

CREATE TABLE `usuarios` (
  `id_usuario` INT NOT NULL AUTO_INCREMENT,
  `id_rol` INT NOT NULL,
  `nombre_completo` VARCHAR(100) NOT NULL,
  `email` VARCHAR(120) NOT NULL,
  `password_hash` VARCHAR(255) NOT NULL,
  `estado` VARCHAR(15) DEFAULT 'ACTIVO',
  PRIMARY KEY (`id_usuario`),
  UNIQUE INDEX `uq_usr_email` (`email`),
  CONSTRAINT `fk_usuarios_roles`
    FOREIGN KEY (`id_rol`)
    REFERENCES `roles` (`id_rol`)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE = InnoDB;
CREATE TABLE `productos` (
  `id_producto` INT NOT NULL AUTO_INCREMENT,
  `id_categoria` INT NOT NULL,
  `sku` VARCHAR(30) NOT NULL,
  `nombre_producto` VARCHAR(120) NOT NULL,
  `precio_unitario` DECIMAL(12,2) NOT NULL,
  `stock_disponible` INT NOT NULL,
  PRIMARY KEY (`id_producto`),
  UNIQUE INDEX `uq_prod_sku` (`sku`),
  CONSTRAINT `chk_prod_precio` CHECK (`precio_unitario` > 0),
  CONSTRAINT `chk_prod_stock` CHECK (`stock_disponible` >= 0),
  CONSTRAINT `fk_productos_categorias`
    FOREIGN KEY (`id_categoria`)
    REFERENCES `categorias` (`id_categoria`)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE = InnoDB;
Protección RESTRICT: Si un usuario tiene el rol 'VENDEDOR', la base de datos rechaza cualquier intento de borrar dicho rol mientras existan usuarios con esa referencia.
Estructura del Script SQL • Paso 4

Bloque DDL: Tablas Transaccionales y Acción en Cascada

pedidos y detalle_pedidos

Se definen las tablas de ventas. Notar cómo detalle_pedidos aplica CASCADE hacia pedidos y RESTRICT hacia productos:

CREATE TABLE `pedidos` (
  `id_pedido` INT NOT NULL AUTO_INCREMENT,
  `id_usuario` INT NOT NULL,
  `numero_factura` VARCHAR(25) NOT NULL,
  `fecha_pedido` DATETIME DEFAULT CURRENT_TIMESTAMP,
  `total_neto` DECIMAL(12,2) NOT NULL DEFAULT 0.00,
  `estado_pedido` VARCHAR(20) DEFAULT 'PENDIENTE',
  PRIMARY KEY (`id_pedido`),
  UNIQUE INDEX `uq_ped_factura` (`numero_factura`),
  CONSTRAINT `chk_ped_total` CHECK (`total_neto` >= 0),
  CONSTRAINT `fk_pedidos_usuarios`
    FOREIGN KEY (`id_usuario`)
    REFERENCES `usuarios` (`id_usuario`)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE = InnoDB;
CREATE TABLE `detalle_pedidos` (
  `id_detalle` INT NOT NULL AUTO_INCREMENT,
  `id_pedido` INT NOT NULL,
  `id_producto` INT NOT NULL,
  `cantidad` INT NOT NULL,
  `precio_unitario` DECIMAL(12,2) NOT NULL,
  `subtotal` DECIMAL(12,2) NOT NULL,
  PRIMARY KEY (`id_detalle`),
  CONSTRAINT `chk_det_cantidad` CHECK (`cantidad` > 0),
  CONSTRAINT `fk_det_pedidos`
    FOREIGN KEY (`id_pedido`) REFERENCES `pedidos` (`id_pedido`)
    ON DELETE CASCADE ON UPDATE CASCADE,
  CONSTRAINT `fk_det_productos`
    FOREIGN KEY (`id_producto`) REFERENCES `productos` (`id_producto`)
    ON DELETE RESTRICT ON UPDATE CASCADE
) ENGINE = InnoDB;
SET FOREIGN_KEY_CHECKS = 1; -- Cierre del bloque DDL y reactivación de chequeos Estructura Física Completa (6 Tablas)

Estructura del Script SQL • Paso 7

Bloque DQL: Consultas de Verificación con INNER JOIN

Validación de Relaciones

Al final del script maestro, incluir 2 o 3 consultas SELECT con INNER JOIN para certificar que el modelo físico cruza los datos correctamente:

-- Consulta A: Catálogo con su Categoría:
SELECT
  p.sku,
  p.nombre_producto,
  c.nombre_categoria,
  CONCAT('$ ', FORMAT(p.precio_unitario, 2)) AS precio,
  p.stock_disponible
FROM productos p
INNER JOIN categorias c ON p.id_categoria = c.id_categoria
ORDER BY c.nombre_categoria ASC;
-- Consulta B: Factura Desglosada (Doble JOIN):
SELECT
  ped.numero_factura,
  u.nombre_completo AS cliente,
  pr.nombre_producto,
  det.cantidad,
  det.precio_unitario,
  det.subtotal
FROM detalle_pedidos det
INNER JOIN pedidos ped ON det.id_pedido = ped.id_pedido
INNER JOIN usuarios u ON ped.id_usuario = u.id_usuario
INNER JOIN productos pr ON det.id_producto = pr.id_producto;
Certificación de Calidad: Cuando el instructor ejecute el script completo, estas consultas mostrarán tablas estructuradas en el panel *Result Grid*, comprobando que la base de datos está 100% viva y operativa.
Técnicas de Exportación

Exportación del Script y Prueba de Cero Errores

MySQL Workbench

La guía exige explícitamente: "Debe generar el script y exportarlo". Existen dos formas de obtener el archivo SQL final:

Método 1: Desde el Modelo Gráfico (EER)
  1. Abre el modelo .mwb en Workbench.
  2. Menú: File > Export > Forward Engineer SQL CREATE Script...
  3. Elige la ruta de guardado: script_estructura_bd.sql.
  4. Marca: "Generate INSERT Statements for Tables" si ya definiste datos en la pestaña Inserts.
  5. Finaliza y guarda el archivo.
Método 2: Desde el Editor de Consultas SQL
  1. Copia y pega la estructura DDL, seeders y consultas en una pestaña nueva.
  2. Presiona Ctrl + Shift + Enter para ejecutar de inicio a fin.
  3. Verifica que todas las filas del Action Output muestren check verde.
  4. Menú: File > Save Script As... guardándolo como script_maestro_bd.sql.
Regla de Aprobación: Antes de comprimir en ZIP, abre una pestaña nueva en Workbench, carga tu archivo .sql y ejecútalo completo. Si no arroja ninguna marca roja (Error Code), tu evidencia está lista para entregar.
