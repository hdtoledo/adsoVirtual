Concepto 1

Sin control de versiones, el equipo trabaja a ciegas

Un sistema de control de versiones registra cada cambio del código: qué cambió, quién lo hizo, cuándo y por qué. Permite volver atrás y trabajar en equipo sin sobrescribirse.

Sin control de versiones

  • proyecto_final.zip
  • proyecto_final_v2.zip
  • proyecto_final_v2_corregido.zip
  • proyecto_FINAL_ahora_si.zip
  • proyecto_final_de_laura.zip
  • ¿Cuál es la versión buena?
  • ¿Quién borró la validación del login?
  • Dos personas editaron el mismo archivo: se pierde trabajo.

Con Git

  • a1f3c9efeat(auth): agregar validación del loginLaura
  • 7b2d410fix(pedidos): corregir total con IVAAndrés
  • c90e1aadocs: actualizar READMESofía
  • Historial completo y una sola versión oficial.
  • Cada cambio tiene autor, fecha y motivo.
  • Ramas para trabajar en paralelo sin pisarse.
  • Copia de seguridad en un servidor remoto.
Concepto 2

Local, centralizado y distribuido

Tu informe debe explicar qué tipo de sistema eliges y por qué. Hoy el estándar de la industria es el modelo distribuido con Git.

Local

Ej.: RCS

Las versiones se guardan solo en el equipo del desarrollador.

Ojo: Sin colaboración; si el disco falla, se pierde todo.

Centralizado

Ej.: Subversion (SVN), CVS

Un servidor central guarda la historia; cada uno descarga una copia de trabajo.

Ojo: Si el servidor cae, nadie puede registrar cambios.

Distribuido Recomendado

Ej.: Git, Mercurial

Cada desarrollador tiene una copia completa del repositorio y su historia.

Ojo: Trabaja sin conexión; cualquier copia sirve de respaldo.

Cada equipo tiene el repositorio completo. Se sincronizan con git push y git pull.

Repositorio remoto

GitHub, GitLab o Bitbucket

git pull / git clone traen los cambios del remoto

Git ≠ GitHub

Git es el programa que guarda versiones en tu equipo. GitHub es un servicio en internet que aloja repositorios Git. Por eso el informe elige ambos: la herramienta y la plataforma.

Local

git init, git add, git commit, git log, git branch: funcionan sin internet.

Remoto

git remote, git push, git pull, git clone: necesitan la plataforma y conexión.

Concepto 4

Nueve palabras que usarás todo el tiempo

Inclúyelas en el informe (como glosario o dentro del texto): demuestran que comprendes la herramienta que seleccionas.

Repositorio

Carpeta del proyecto con toda su historia de cambios.

Commit

Foto del proyecto en un momento, con autor, fecha y mensaje.

Rama (branch)

Línea de trabajo paralela; permite desarrollar sin afectar la versión estable.

Merge

Unir los cambios de una rama en otra.

Pull request

Solicitud para revisar y unir una rama en la plataforma remota.

Remoto

Copia del repositorio alojada en un servidor (origin).

Clone

Descargar un repositorio remoto completo a tu equipo.

Tag

Etiqueta que marca una versión importante, como v1.0.0.

.gitignore

Lista de archivos que Git no debe versionar (dependencias, secretos).

Plan · Paso 1

¿Cómo trabajará el equipo en paralelo sin romper la versión estable?

La estrategia de ramas (branching) es parte del plan de trabajo. Las dos más conocidas son GitHub Flow y Git Flow.

GitHub Flow Elegida

  • Una rama estable: main.
  • Cada tarea en una rama feature/… que vuelve por pull request revisado.
  • Simple: ideal para equipos pequeños y entregas frecuentes.

Git Flow

  • main para producción y develop para integración.
  • Ramas de feature, release y hotfix.
  • Útil con versiones planificadas y equipos grandes; más pasos.

Justificación: AromaSur es un equipo de 3 personas que entrega por evidencias: GitHub Flow da orden sin la complejidad de Git Flow. Escribe en el informe cuál eliges y por qué.

Plan · Paso 6

Así se trabaja cada tarea del plan

Incluye este flujo en el informe como "procedimiento de trabajo". Los comandos funcionan igual en PowerShell, Git Bash y la terminal de VS Code.

PowerShell 
# 1. Traer lo último de main
git switch main
git pull origin main

# 2. Crear la rama de la tarea
git switch -c feature/catalogo-filtros

# 3. Trabajar y registrar cambios pequeños
git add .
git commit -m "feat(catalogo): filtrar cafés por perfil"

# 4. Subir la rama y abrir el pull request en GitHub
git push -u origin feature/catalogo-filtros

# 5. Tras la aprobación del PR: actualizar main y borrar la rama local
git switch main
git pull origin main
git branch -d feature/catalogo-filtros

Reglas del equipo

  • Nadie trabaja directamente en main.
  • Commits pequeños con un solo propósito.
  • Hacer git pull antes de empezar cada día.
  • Todo pull request lo revisa otra persona.
  • Proteger main en GitHub para exigir pull request.

Comprueba la instalación con git --version. La salida esperada se parece a git version 2.x.x.windows.1; la instalación paso a paso es la EV04.

Cómo se ve una buena introducción, objetivo y justificación

Ejemplo con AromaSur para que veas el nivel esperado. Escribe el tuyo con los datos de tu proyecto: un texto copiado no demuestra el criterio.

Introducción

"La plataforma de pedidos mayoristas de AromaSur Café permitirá a cafeterías y tiendas consultar el catálogo, hacer pedidos y seguir su estado. Su construcción involucra una API, una aplicación web en React y una base de datos, desarrolladas por un equipo de tres aprendices. Para coordinar el trabajo, conservar el historial de cambios y recuperar versiones anteriores, el proyecto requiere un sistema de control de versiones. Este informe presenta la selección de esas herramientas y el plan de trabajo para construir el software."

Objetivo

"Seleccionar y justificar las herramientas y tecnologías de versionamiento que se utilizarán en la construcción de la plataforma AromaSur, y definir el plan de trabajo con su estrategia de ramas, convenciones y etapas de desarrollo."

Justificación (fragmento)

"Se selecciona GitHub como plataforma remota porque obtuvo el mayor puntaje en la matriz ponderada (96 %): ofrece repositorios privados sin costo para el equipo, GitHub Actions para validar cada pull request y GitHub Pages para publicar la demo de la aplicación web."

El porcentaje sale de la matriz con los pesos por defecto.
